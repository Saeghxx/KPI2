# DEFENSE — Завдання 1: Домен і модель даних (ER)

## 1. Намір і критерії

Спроєктувати ER-модель онлайн-магазину книг у 3NF з UUID/PK/FK, прямими зв'язками N:M та асоціативною сутністю лише там, де зв'язок має власні атрибути. Критерії 1–8 зафіксовано в `spec.md`.

## 2. Топ-3 розбіжності (spec ↔ вихід AI) + коміт-виправлення

- Id без `PK` і відсутні `FK` у 1:N (Book, CustomerOrder, Review), час як `datetime` → критерії 1, 5, 6 у spec (коміт: `ac76591`; `ai/prompt-1.md`, `ai/prompt-2.md`).

- `CustomerOrder.total_price` — похідне поле, порушення 3NF → критерій 2 у spec забороняє похідні, поле прибрано зі spec (коміт: `<SHA>`; `ai/prompt-3.md`).

- Прямий N:M Order–Book втрачав `quantity` і ціну на момент покупки → у spec додано OrderItem і правило асоціативної сутності (критерій 3) (коміт: `<SHA>`; `ai/prompt-3.md`).

Усі виправлення — зміною spec/критеріїв і повторною генерацією, не ручним патчем діаграми. Додатково знайдено відсутність `UK` для `email`/`isbn` → критерій 8.

## 3. Ключове рішення

OrderItem як асоціативна сутність, а не прямий N:M Order–Book: зв'язок має `quantity` і `unit_price`. Альтернатива (прямий N:M) втрачає ці дані й історичну ціну (`adr/0001-order-item-associative-entity.md`; див. також `adr/0002`, `adr/0003`).

## 4. Перевірка

Попередньої моделі немає (це перше завдання), тому перевірено узгодженість spec ↔ модель: 8 сутностей у spec = 8 у діаграмі; імена полів збігаються (`price`, `unit_price`); усі `id` — `UUID PK`; кожен 1:N має `FK` на боці «багато»; кожен критерій 1–8 пройдено в `ai/prompt-4.md`.
