# ADR-0001: Вибір інструмента для sequence-діаграм

- **Статус:** Accepted
- **Дата:** 2026-10-29

## Context and Problem Statement

Для Lab3 потрібно створити sequence-діаграми SC-09–SC-12 для UC-06 «Оплата замовлення». Діаграми мають відображати учасників, виклики та повернення, activation bars і фрагменти `opt`, `loop`, `alt`. Потрібен інструмент, який дозволяє зберігати діаграми як текст у репозиторії та перевіряти їхню відповідність `Lab3/spec.md` і Gherkin.

## Decision Drivers

1. Відповідність вимогам до sequence-діаграм: повідомлення, фрагменти й activation bars.
2. Зручне зберігання діаграм у Git та перегляд змін у комітах.
3. Простота редагування й перевірки діаграм за специфікацією.
4. Можливість відтворити діаграму з текстового опису без ручного перемальовування.
5. Рендеринг діаграм безпосередньо в GitHub Markdown без додаткових файлів.

## Considered Options

### Option 1: Mermaid

**Плюси**
- Діаграми описуються текстом і зберігаються безпосередньо в репозиторії.
- Зміни легко переглядати в Git.
- Sequence-діаграми підтримують учасників, повідомлення, `opt`, `loop` та `alt`.
- GitHub рендерить Mermaid-діаграми безпосередньо в Markdown, тому не потрібно зберігати окремі PNG/SVG-файли.

**Мінуси**
- Спільну послідовність між діаграмами потрібно повторювати вручну: немає механізму `ref`, який дозволив би винести її в окремий повторно використовуваний фрагмент.
- Точне оформлення activation bars і повернень потрібно перевіряти за результатом рендерингу.

### Option 2: PlantUML

**Плюси**
- Текстовий опис зберігається в Git.
- Підтримує sequence-діаграми, фрагменти взаємодії та activation bars.
- Має засоби повторного використання описів, зокрема через включення файлів.

**Мінуси**
- Для перегляду рендеру в GitHub потрібно додатково генерувати й комітити PNG/SVG-файли діаграм.

### Option 3: draw.io

**Плюси**
- Візуальне редагування дає змогу вручну контролювати розташування учасників, стрілок і фрагментів.
- Зручно для діаграм, де важливе точне компонування.

**Мінуси**
- Ручне редагування та вирівнювання елементів збільшують обсяг роботи під час змін.
- Зміни у візуальному файлі складніше перевіряти як текстову різницю в Git.
- Автоматична генерація з текстової специфікації менш пряма, ніж у текстових мовах діаграм.

## Decision Outcome

Обрано **Mermaid**, оскільки він підтримує текстовий опис sequence-діаграм, зберігання в Git і перевірку за `spec.md`, а також рендериться безпосередньо в GitHub Markdown без додаткових PNG/SVG-файлів. Саме остання перевага відрізняє Mermaid від PlantUML у межах визначених критеріїв вибору.

## Consequences

**Позитивні наслідки**
- Діаграми зберігаються поруч зі специфікацією та змінюються через коміти.
- Текст діаграми можна перевіряти на відповідність критеріям прийняття.
- Зміни назв повідомлень і умов фрагментів можна відстежувати в Git.

**Негативні наслідки та контроль**
- Спільна послідовність SC-09 повторюється в SC-10–SC-12, оскільки Mermaid не має механізму `ref` для повторного використання фрагмента sequence-діаграми. Контроль: критерій
