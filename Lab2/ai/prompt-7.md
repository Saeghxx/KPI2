# ADR-001: Визначення меж сценаріїв онлайн-книгарні

**Статус:** Прийнято

## 1. Контекст

Під час моделювання Use Cases для онлайн-книгарні необхідно визначити межі сценаріїв так, щоб вони відображали поведінку системи, взаємодію з акторами та можливі результати виконання операцій.

Основні процеси системи — пошук книг, реєстрація покупця, керування кошиком, оформлення замовлення, оплата, доставка, скасування замовлення та застосування промокоду — мають різні умови виконання й результати.

Один сценарій може завершитися успішно або перейти до альтернативного результату, наприклад через відмову платіжного шлюзу, тайм-аут чи недійсний промокод. Водночас надмірне подрібнення сценаріїв ускладнює підтримку моделі та робить її менш зрозумілою.

Тому потрібно обрати спосіб декомпозиції, який забезпечує зрозумілі межі Use Cases, відокремлює обов’язкову поведінку від умовної та враховує взаємодію із зовнішніми системами.

## 2. Рішення

Прийнято такі правила моделювання:

1. **Розділяти сценарії за результатом рішення системи.** Успішний результат і суттєві альтернативні результати, зокрема відмови, тайм-аути та відхилення операцій, описуються окремими сценаріями в межах відповідного Use Case. Окремий Use Case створюється лише тоді, коли поведінка має самостійну мету або виправдану повторну використовуваність.
2. **Виділити оплату в окремий Use Case «Оплата замовлення».** Платіжний шлюз визначається як зовнішній актор, який взаємодіє із системою під час обробки платежу. Use Case «Оформлення замовлення» включає Use Case «Оплата замовлення» через `<<include>>`, якщо оплата є обов’язковою частиною саме цього сценарію оформлення. Якщо замовлення створюється до оплати й може існувати зі статусом `new`, оплату слід моделювати як окремий сценарій, що запускається після оформлення, а не як обов’язковий `include`.
3. **Моделювати застосування промокоду через `<<extend>>`.** Застосування промокоду є умовною поведінкою, яка виконується лише тоді, коли покупець вирішує використати промокод. Основний сценарій оформлення замовлення може завершитися і без промокоду.
4. **Описувати відмови як альтернативні потоки.** Для оплати передбачаються окремі сценарії успішної оплати, відмови платіжного шлюзу та відсутності відповіді протягом визначеного часу. Для промокоду описуються, зокрема, недійсний або прострочений код. Це дає змогу перевіряти кожний результат окремо.

## 3. Розглянуті альтернативи

### Альтернатива A: Один великий Use Case «Купити книгу»

Усі кроки — від пошуку книги до оплати й доставки — об’єднуються в один Use Case.

**Причини відхилення:**

- сценарій стає надто великим і складним для читання;
- складніше відокремити відповідальність покупця, системи та зовнішніх сервісів;
- численні альтернативні потоки ускладнюють тестування й трасування вимог;
- окремі операції, наприклад оплата, не можна легко повторно використати в інших сценаріях.

### Альтернатива B: Окремий Use Case для кожного кроку форми

Кожна дія інтерфейсу, наприклад введення адреси, натискання кнопки або вибір способу оплати, моделюється як окремий Use Case.

**Причини відхилення:**

- Use Cases мають описувати цілі актора, а не кожну дію інтерфейсу;
- модель стає надмірно деталізованою та залежною від поточного дизайну форми;
- зміни інтерфейсу спричинятимуть зайві зміни діаграми;
- основні бізнес-процеси стають менш помітними.

### Альтернатива C: Оплата як `<<extend>>`

Use Case «Оплата замовлення» розширює Use Case «Оформлення замовлення» лише за певної умови.

**Причини відхилення:**

- `<<extend>>` означає умовну додаткову поведінку, а не обов’язкову складову базового сценарію;
- якщо оплата завжди виконується в межах обраного сценарію оформлення, `<<extend>>` не відображає цю обов’язковість;
- зв’язок слід обирати за фактичною логікою процесу, а не лише для скорочення діаграми.

**Уточнення:** якщо замовлення створюється незалежно від оплати й покупець може оплатити його пізніше, найточніше рішення — окремі Use Cases «Оформлення замовлення» та «Оплата замовлення» без `include` між ними. Це відповідає моделі, у якій замовлення спочатку отримує статус `new`, а після успішної оплати — `paid`.

## 4. Наслідки

### Позитивні

- межі Use Cases відповідають цілям акторів і бізнес-процесам;
- успішні та помилкові результати можна тестувати окремо;
- зовнішня взаємодія з платіжним шлюзом явно представлена в моделі;
- умовна поведінка промокоду не ускладнює основний сценарій;
- спрощується трасування зв’язків між вимогами, Use Cases і тестовими сценаріями.

### Негативні

- кількість альтернативних потоків і тестових сценаріїв збільшується;
- потрібно підтримувати узгодженість між Use Cases, вимогами та тестами;
- необхідно чітко визначити, які операції є обов’язковими, а які — умовними.

### Підсумок

Обрано декомпозицію за бізнес-цілями та суттєвими результатами сценаріїв. Відмови описуються окремими альтернативними потоками, оплата моделюється як самостійний Use Case із зовнішнім актором «Платіжний шлюз», а застосування промокоду — як умовне розширення основного сценарію через `<<extend>>`. Тип зв’язку між оформленням замовлення та оплатою визначається фактичним процесом: `<<include>>` застосовується лише тоді, коли оплата обов’язкова в межах базового Use Case.

Важливий нюанс для твоєї ER-моделі: оскільки `CustomerOrder.status` має значення `new`, `paid`, `shipped` і `cancelled`, а вимоги FR-05–FR-07 описують оплату вже створеного замовлення, логічніше залишити оплату окремим Use Case без `include` від оформлення замовлення. Це узгоджує ADR із життєвим циклом замовлення.



## Що виправлено вручну
- Прибрано всі згадки про промокод: у моїй специфікації немає ні вимоги, ні use case для промокоду.
- Прибрано include між «Оформленням» і «Оплатою»: у діаграмі оплата окремий use case; include є між UC-06 і UC-07, extend між UC-08 і UC-06.
