# DEFENSE — Завдання 2: Вимоги та Use Cases

## Намір і критерії (1–2 речення)

Я описала поведінку онлайн-книгарні EARS-вимогами, user stories й Gherkin-сценаріями та показала зв'язок між ними матрицею трасування й use-case діаграмою. Критерії: вимоги однозначні й перевіряються (є числа, статуси, умови помилки), трасування багато-до-багатьох, актори й сутності узгоджені з ER-моделлю з Завдання 1, а непокриті елементи позначені й пояснені.

## Топ-3 розбіжності (spec ↔ артефакт) + коміт-виправлення

- `Customer` в ER мав лише `id`, `email`, `full_name`, а вимоги потребують пароля (хеш), адреси, телефону й ролі адміністратора (FR-02, FR-08, FR-11, FR-12). Додала `password_hash`, `role`, `phone`, `address`. Коміт: `b2c13c4`
- В ER не було даних для оплати й доставки: ідентифікатора транзакції, результату платежу, ідентифікатора відправлення (FR-06–FR-08). Додала сутності `Payment` і `Shipment`. Коміт: `b2c13c4`
- `Category` і wishlist були в ER, але жодна вимога чи use case їх не використовує. Позначила їх поза обсягом цієї ітерації й виправила цілі акторів у spec. Коміт: `b2c13c4`

Окремо уточнила, що кошик існує лише в сесії й не є сутністю ER (FR-03, UC-03).

## Ключове рішення — які альтернативи зважила і чому обрала цю (ADR)

Я вирішувала, де проводити межі use cases і сценаріїв. Розглянула три варіанти: один великий use case «Купити книгу», use case на кожен крок форми й оплату як include або extend від оформлення. Обрала use case за ціллю актора, а сценарії за рішенням системи (успіх і кожна відмова окремо), оплату окремим use case з актором Платіжний шлюз. Замовлення створюється зі статусом `new` ще до оплати, тому include від оформлення не підходить, а extend робив би основну ціль покупця необов'язковою. Повний ADR: `Lab2/adr/0001-use-case-boundaries.md`.

## Перевірка — узгодженість із попередньою моделлю (як перевірила)

Я пройшла по кожному актору й use case і шукала відповідну сутність в ER, потім по кожній вимозі й шукала атрибут, потрібний для її перевірки (наприклад, для FR-12 поле `password_hash`, для FR-06 `transaction_id`). Потім пішла у зворотний бік: по кожній сутності ER шукала use case, який її використовує, і так знайшла `Category` і wishlist без use case. Матрицю трасування перевірила в обидва боки (вимога → сценарій/UC і UC → вимоги): непокрита FR-12 (нефункціональна, перевіряється модульним тестом) і UC-05 (немає сценарію з порожнім кошиком). Оновлена модель лежить у `Lab2/model/er.md`.
