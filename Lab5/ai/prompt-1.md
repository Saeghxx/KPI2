## **2. Неоднозначності й суперечності в самому Lab5/spec.md**

### **2.1. Критерії прийняття**

1. **Критерій 1 — трасування компонентів.** Не визначено, чи достатньо посилання на сутність ER для Data Access і БД, оскільки вони не мають власних FR/UC.
2. **Критерій 2 — один provider.** Не уточнено, чи IRepository може мати п'ятьох споживачів одночасно. Це допустимо, якщо provider один — Data Access.
3. **Критерій 3 — відповідність операцій Sequence.** Для IAccounts, ICatalog, IOrders та IApi операції не перелічені. Тому перевірити повну відповідність цьому критерію неможливо.
4. **Критерій 5 — відсутність циклів.** Не визначено, чи зворотні повідомлення-відповіді в інтерфейсах вважаються залежностями. Це важливо для IPayments.
5. **Критерій 7 — власність сутностей.** Не визначено, чи компонент-власник лише відповідає за бізнес-логіку сутності, чи також за всі операції читання та запису.

### **2.2. Назви й напрямки інтерфейсів**

| Інтерфейс         | Неоднозначність                                                                                                      |
| ----------------- | -------------------------------------------------------------------------------------------------------------------- |
| IApi              | API надає інтерфейс Web UI, але його операції не визначені.                                                          |
| IAccounts         | Не визначені операції реєстрації, входу та керування обліковими записами.                                            |
| ICatalog          | Не визначені операції каталогу й відгуків.                                                                           |
| IOrders           | Не визначені операції створення, перевірки та скасування замовлення.                                                 |
| IPayments         | `processPayment(orderId, amount)` — не уточнено, хто ініціює виклик і чи збігається він із повідомленням у Sequence. |
| IShipping         | `submitShipment(orderId)` — умовна операція, відсутня в Lab3.                                                        |
| IPaymentGateway   | `chargeOrder(orderId, amount)` збігається з Lab3.                                                                    |
| IDeliveryProvider | `createShipment(orderId)` — умовна операція, відсутня в Lab3.                                                        |
| IRepository       | Перелік операцій неповний, оскільки для частини сутностей операції визначатимуться під час створення діаграми.       |
| ISql              | Не визначено, які саме SQL-операції надає БД.                                                                        |

**Важливий момент щодо IPayments та IShipping:** у специфікації зазначено напрямок від provider до consumer. Але операції `processPayment` і `submitShipment` за змістом викликаються споживачем. Потрібно чітко розділити напрямок надання інтерфейсу та напрямок виклику операції.

### **2.3. Межа системи**

1. Зовнішні платіжний шлюз і служба доставки визначені однозначно.
2. Не сказано прямо, чи БД входить у межу системи. За структурою специфікації вона виглядає внутрішньою частиною системи.
3. Не визначено, чи Web UI та API є двома окремими компонентами всередині однієї межі.
4. Моноліт і окремі компоненти не суперечать один одному: компонентна діаграма може показувати логічно розділені модулі одного застосунку. Але це варто відрізняти від фізично незалежних сервісів.

### **2.4. Інші суперечності**

- **PaymentService / OrderService:** PaymentService повертає результат оплати OrderService, але не визначено, кому належить відповідальність за обробку помилки й остаточне оновлення замовлення.
- **ShippingService / OrderService:** не визначено, хто саме змінює `CustomerOrder.status` на `shipped` після підтвердження доставки.
- **NotificationSent:** у Lab4 це окремий стан, але в Lab5 немає компонента сповіщень. Замість цього повідомлення проходить через OrderService та API. Потрібно розмежувати формування повідомлення й відображення його у Web UI.
- **Payment і база даних:** PaymentService є власником Payment, а Data Access — єдиною точкою доступу до БД. Не уточнено, чи PaymentService зберігає дані виключно через IRepository, чи має додатковий прямий доступ.
- **API та AccountService:** авторизація вказана в API, а роль і пароль належать AccountService. Це потенційне накладання відповідальності.

## **3. Уточнювальні питання**

Це питання, на які наразі немає однозначної відповіді у специфікації. Рішення залишаю за тобою.

1\. **Архітектура:** підтверджуєш моноліт з логічно відокремленими компонентами чи розглядаєш фізично незалежні сервіси?

2\. **Payment:** PaymentService має бути внутрішнім компонентом моноліту чи окремим сервісом із власною БД?

3\. **API:** чи повинен API відповідати тільки за приймання запитів і сесії, чи також за авторизацію та перевірку ролей?

4\. **AccountService:** чи залишаємо в ньому вхід і керування ролями, попри відсутність відповідних UC у Завданні 2?

5\. **IPayments:** хто ініціює `processPayment(orderId, amount)` — OrderService чи API? Чи є ця операція в повній Sequence-діаграмі Lab3?

6\. **Доставка:** хто змінює `CustomerOrder.status` на `shipped` після підтвердження служби доставки — ShippingService чи OrderService?

7\. **Відмова доставки:** хто формує повідомлення про помилку передавання замовлення — ShippingService, OrderService чи API?

8\. **NotificationSent:** чи залишається формування повідомлень відповідальністю OrderService, а їх відображення — Web UI?

9\. **Інтерфейси:** чи потрібно перелічити конкретні операції IAccounts, ICatalog, IOrders та IRepository, чи достатньо показати інтерфейси без повної деталізації методів?

10\. **Межа системи:** чи правильно розуміти, що БД, Data Access, API, Web UI та всі п'ять сервісів розташовані всередині системи, а платіжний шлюз і служба доставки — поза нею?

Усі компоненти працюють як частини одного застосунку. PaymentService — внутрішній модуль, Payment зберігається у спільній БД через Data Access.

**Переваги:**

- Просте розгортання та тестування.

### **Порівняння трьох варіантів**

| Критерій              | A. Моноліт        | B. Модульний моноліт | C. Мікросервіси    |
| --------------------- | ----------------- | -------------------- | ------------------ |
| Розгортання           | Одне              | Одне                 | Незалежне          |
| Межі компонентів      | Логічні           | Чіткі                | Фізичні й логічні  |
| БД                    | Спільна           | Переважно спільна    | Окрема для сервісу |
| Складність            | Низька            | Середня              | Висока             |
| Масштабування Payment | Разом із системою | Разом із системою    | Незалежне          |

**Окремо про Payment:** вибір між цими варіантами не означає, що Payment обов'язково повинен мати окрему БД. Можливі різні комбінації: окремий логічний модуль зі спільною БД або незалежний сервіс із власним сховищем.

**Підсумок аудиту:** найбільше невизначеностей зараз стосується меж відповідальності API, OrderService, PaymentService і ShippingService, а також напрямків IPayments та IShipping. Сам перелік компонентів загалом узгоджується з попередніми роботами. Критичних суперечностей, які роблять компонентну модель неможливою, немає, але до уточнення цих питань діаграма матиме неоднозначні місця.

Після твоїх відповідей можна буде повторно перевірити узгодженість специфікації, не змінюючи твоїх архітектурних рішень.

## **4. Що ще потрібно контролювати під час побудови діаграми**

Залишаються не архітектурні суперечності, а моменти, які потрібно правильно відобразити:

1. **IPayments:** provider — PaymentService, consumer — OrderService.
2. **IShipping:** provider — ShippingService, consumer — OrderService.
3. **IRepository:** один provider — Data Access; споживачі — сервіси.
4. **ISql:** provider — БД, consumer — Data Access.
5. **IAccounts:** API використовує його для перевірки ролі.
6. **Доставка:** ShippingService не змінює CustomerOrder.status. Це робить OrderService.
7. **Повідомлення:** окремий NotificationService не потрібен.
8. **Payment:** не потребує окремої БД.
9. **Межа системи:** платіжний шлюз і служба доставки зовнішні.

**Висновок:** твоїх відповідей достатньо, щоб однозначно визначити основну структуру компонентної діаграми. Нових уточнювальних питань зараз немає.
